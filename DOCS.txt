DMMR PROJECT - TECHNICAL NOTES
=============================

Repository structure:
- nginx-dmmr-module-c/: Nginx module implemented in C
- http_dmmr_cache/: local cache daemon backed by Berkeley DB

Main components:
1. Nginx module
   - Handles auth, routing, rate limiting and proxying with token support and configurable rate windows
   - Reads the directive dmmr_cache_addr
   - Uses the configured cache endpoint for lookups

2. Cache daemon
   - Exposes a custom binary protocol for key lookup/update/delete
   - Supports Unix sockets and TCP
   - Persists data in Berkeley DB (apikeys.db)

Cache address formats:
- unix:/run/dmmr/dmmr_cache.sock
- tcp:127.0.0.1:9080

Runtime behavior:
- The Nginx module sends a request to the cache daemon when an API key is presented
- The daemon returns a binary protocol status and optional payload
- Missing or invalid keys return 403; missing credentials return 401
- Cache connectivity failures return 503; there is no static-key fallback

Build and run:
- cd http_dmmr_cache
- make
- ./dmmr_cache --unix
- ./dmmr_cache --tcp
- ./dmmr_cache --both

Example curl commands:
- Unix socket:
  The cache protocol is binary; use the project's Python tests/client rather
  than curl.
- TCP:
  The cache protocol is binary; use the project's Python tests/client rather
  than curl.

Configuration example:
location / {
    dmmr_enable on;
    dmmr_cache_addr unix:/run/dmmr/dmmr_cache.sock;
}

WSL/Linux with systemd Nginx:
- Some Nginx services use PrivateTmp=true, which isolates /tmp from the
  daemon launched in a shell. In that case, /tmp/dmmr_cache.sock is not visible
  to Nginx and produces 503 responses.
- Create a shared runtime directory and configure all processes with the same
  socket path:
  sudo install -d -o "$USER" -g "$(id -gn)" -m 0777 /run/dmmr
  export DMMR_SOCKET_PATH=/run/dmmr/dmmr_cache.sock
  export DMMR_SOCKET_MODE=0666
- The cache cluster listener defaults to port 9081. If Nginx also listens on
  9081, avoid the collision with: export DMMR_CLUSTER_PORT=9091

Runtime environment variables:
- DMMR_BIND_ADDRESS: IPv4 address for the cache TCP listener (default 127.0.0.1)
- DMMR_CACHE_PORT: cache TCP port (default 9080)
- DMMR_CLUSTER_PORT: cluster listener port (default 9081)
- DMMR_CLUSTER_SEEDS: comma-separated seed nodes for auto-discovery (e.g. 10.0.0.1:9081)
- DMMR_ADVERTISE_ADDRESS: IP address advertised to cluster peers
- DMMR_CLUSTER_NAME: cluster name for isolation (nodes with different names reject HELLO)
- DMMR_DB_PATH: Berkeley DB file path (default ./apikeys.db)
- DMMR_WORKERS: number of cache workers (default 4)
- DMMR_SOCKET_PATH: Unix socket path (default /tmp/dmmr_cache.sock)
- DMMR_SOCKET_MODE: Unix socket mode in octal, for example 0660 or 0666

CLI Options for Cluster:
- --seeds=IP:PORT,...    Seeds for cluster discovery
- --advertise=IP         IP address to advertise
- --cluster-name=NAME    Cluster isolation name

Implementation notes:
- Berkeley DB is used as the persistence layer;
- DELETE operations are stored as tombstones so removals propagate consistently through the cluster;
- GET handling returns a not-found status for missing keys instead of a generic error;
- Cluster peers are reaped when they become stale or unreachable, avoiding resource leaks and stale connections;
- Cluster frames validate cluster identity and discovery can recover from seeds and known peers;
- The module opens a cache connection for each authentication lookup and closes it after the response;
- Socket failures are retried and then reported as 503;
- The rate limiting logic uses an in-memory tree and should be evolved to shared memory for multi-worker environments.

Memory pools (http_dmmr_cache/dmmr_pool.c):
- payload_buf, job_pool_entry, control_cmd_pooled and delete_entry use fixed-size chunks for stable metadata.
- Each chunk contains POOL_INITIAL_SIZE entries (configured in dmmr_config.h). A new chunk is allocated only when its pool's free list is empty; existing entries are never moved.
- Each pool has a TAILQ free list protected by its own mutex. get_* removes the first free entry and release_* clears and reinserts it, both in O(1).
- Pointers returned by get_* remain valid while the caller owns the entry. control_cmd_pooled and delete_entry must be removed from their processing queue before release_*, because their TAILQ link is then reused by the pool free list.
- Payload buffers are sized to each frame. Buffers over 64 KiB are freed on release; smaller payload buffers may be retained. Broadcast values are dynamically allocated only while queued.
- destroy_pools releases all chunks and any retained payload or command buffers when the daemon stops.

Stability test:
- Test 14 in tests/suite_tests.py runs 20 seconds of load warm-up before taking the RSS baseline, then monitors the peak RSS for 40 seconds.
- Warm-up excludes normal page commitment while chunks are first used; the test still fails if RSS grows more than 20% after the baseline.

Known beta limitation:
- Graceful daemon shutdown is not yet reliable because the cluster listener can remain blocked in accept(). The current integration suite may need to force-kill the cache process during cleanup.
